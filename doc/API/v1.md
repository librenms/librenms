# API v1 (Beta)

!!! warning "Beta"
    The v1 API is in **beta**. Endpoints and behaviour may change without
    notice while it is under active development. Full endpoint documentation
    is coming later — for now this page covers the basics and how to extend
    it. The stable, fully documented API remains [v0](index.md).

    The v1 API is disabled by default. Enable it with
    `lnms config:set api.v1.enabled true`, or in the web UI under
    **Settings → API → API v1 (Beta)**. When disabled, all `/api/v1`
    endpoints return 404.

## Overview

The v1 API is served under the `/api/v1` prefix and is built on
[Laravel Restify](https://restify.binarcode.com/) with
[Sanctum](https://laravel.com/docs/sanctum) bearer-token authentication.

## Authentication

Most v1 endpoints require a personal access token sent as a standard Bearer token:

```curl
curl -H 'Authorization: Bearer YOURAPITOKENHERE' https://librenms.org/api/v1/system
```

Create an API token from the web interface at `/api-access/` (**Settings → API Settings → API Access**). Note that `X-Auth-Token` is only supported on API v0 endpoints; API v1 strictly requires the `Authorization: Bearer` header.

The token's user must have the `api.access` permission for every endpoint
except `/api/v1/health`. Beyond that, each resource is authorized with the
same permissions as the web UI.

## Available endpoints

| Method          | Path                       | Auth          | Description                                      |
|-----------------|----------------------------|---------------|--------------------------------------------------|
| `GET`           | `/api/v1/health`           | none (public) | Rate-limited readiness probe.                    |
| `GET`           | `/api/v1/system`           | bearer token  | Application version and database row statistics. |
| `GET`           | `/api/v1/alert-rules`      | bearer token  | List alert rules.                                |
| `POST`          | `/api/v1/alert-rules`      | bearer token  | Create an alert rule.                            |
| `GET`           | `/api/v1/alert-rules/{id}` | bearer token  | Show an alert rule.                              |
| `PUT`, `PATCH`  | `/api/v1/alert-rules/{id}` | bearer token  | Update an alert rule.                            |
| `DELETE`        | `/api/v1/alert-rules/{id}` | bearer token  | Delete an alert rule.                            |

More endpoints will be added as the v1 API matures.

## Errors

Errors are returned as a [JSON:API error document](https://jsonapi.org/format/#errors)
with an `errors` array:

```json
{
  "errors": [
    {
      "status": "403",
      "title": "Forbidden",
      "detail": "You do not have the necessary permissions to access this resource."
    }
  ]
}
```

| Status | Cause                                                              |
|--------|--------------------------------------------------------------------|
| 401    | Missing or invalid bearer token.                                   |
| 403    | The user lacks `api.access` or the permission for this action.     |
| 404    | Unknown resource or record, or the v1 API is disabled.             |
| 422    | The request body failed validation.                                |
| 429    | Rate limit exceeded.                                               |
| 503    | A required service, such as the database, is unavailable.          |

Other statuses use the HTTP reason phrase as `title`. Server errors have a
generic `detail`.

A validation failure has one entry per failed rule, and `source.pointer`
names the attribute:

```json
{
  "errors": [
    {
      "status": "422",
      "title": "Unprocessable Content",
      "detail": "The name field is required.",
      "source": { "pointer": "/name" }
    }
  ]
}
```

### Health

`GET /api/v1/health` is public so it can report a failure even when
database-backed token authentication is unavailable. Its response is
deliberately generic: it does not identify dependencies or include exception
messages, application details, or user information. Requests are limited to
60 per minute per client.

A healthy response returns HTTP 200:

```json
{
  "meta": {
    "status": "healthy"
  }
}
```

An unavailable dependency returns a generic HTTP 503:

```json
{
  "errors": [
    {
      "status": "503",
      "title": "Service Unavailable",
      "detail": "A required service is unavailable."
    }
  ]
}
```

### System

`GET /api/v1/system` requires a bearer token. It returns application
identity and selected table row counts:

```json
{
  "meta": {
    "application": {
      "name": "LibreNMS",
      "version": "26.7.0"
    },
    "statistics": {
      "devices": 42,
      "ports": 512,
      "users": 3
    }
  }
}
```

If the database is unavailable during authentication or while gathering
statistics, the endpoint returns the same generic JSON:API 503 error used by
the health endpoint. Database connection details are never included.

### Alert rules

`/api/v1/alert-rules` uses the same permissions as the alert rules page:

| Request          | Permission                                                                            |
|------------------|---------------------------------------------------------------------------------------|
| List, show       | `alert-rule.viewAll`, or `alert-rule.view` for rules mapped to devices the user can access. |
| Create           | `alert-rule.create`                                                                   |
| Update           | `alert-rule.update`                                                                   |
| Delete           | `alert-rule.delete`                                                                   |

A rule is returned as a resource object:

```json
{
  "data": {
    "id": "12",
    "type": "alert-rules",
    "attributes": {
      "name": "Device Down",
      "severity": "critical",
      "isEnabled": true,
      "builder": {
        "condition": "AND",
        "rules": [
          { "id": "devices.status", "field": "devices.status", "type": "integer", "operator": "equal", "value": "0" }
        ],
        "valid": true
      },
      "query": "SELECT * FROM devices WHERE (devices.device_id = ?) AND devices.status = 0",
      "overridesQuery": false,
      "isConditionInverted": false,
      "isMuted": false,
      "sendsRecoveryAlerts": true,
      "sendsAcknowledgementAlerts": true,
      "notifiesPerEntity": false,
      "maximumEntities": null,
      "procedure": null,
      "notes": null,
      "isScopeInverted": false,
      "alertOperationId": null
    }
  }
}
```

| Attribute                    | Type            | Description                                                                                  |
|------------------------------|-----------------|----------------------------------------------------------------------------------------------|
| `name`                       | string          | Required, unique. At most 255 characters.                                                    |
| `severity`                   | string          | Required. `ok`, `warning` or `critical`.                                                     |
| `isEnabled`                  | boolean         | Whether the rule is evaluated. Defaults to `true`.                                           |
| `builder`                    | object          | The rule as built in the web UI rule builder. Required unless `overridesQuery` is `true`.     |
| `query`                      | string          | The SQL the rule runs. Generated from `builder`, unless `overridesQuery` is `true`.          |
| `overridesQuery`             | boolean         | Run `query` as written instead of the query generated from `builder`. Defaults to `false`.   |
| `isConditionInverted`        | boolean         | Alert when the rule does not match. Defaults to `false`.                                     |
| `isMuted`                    | boolean         | Do not send alerts for this rule. Defaults to `false`.                                       |
| `sendsRecoveryAlerts`        | boolean         | Send an alert when the rule recovers. Defaults to `true`.                                    |
| `sendsAcknowledgementAlerts` | boolean         | Send an alert when the alert is acknowledged. Defaults to `true`.                            |
| `notifiesPerEntity`          | boolean         | Send a separate alert for each matching entity. Defaults to `false`.                         |
| `maximumEntities`            | integer or null | Limit on the number of entities alerted on.                                                  |
| `procedure`                  | string or null  | Procedure text or URL. At most 80 characters.                                                |
| `notes`                      | string or null  | Free-form notes.                                                                             |
| `isScopeInverted`            | boolean         | Read-only. Whether the rule applies to every device except its devices, groups and locations. |
| `alertOperationId`           | integer or null | ID of the alert operation that sends the rule's notifications.                               |

Rules created through the API apply to all devices. Device, group and
location mappings are edited in the web UI for now.

`GET /api/v1/alert-rules` is paginated (`page`, `perPage`) and accepts:

| Parameter                                | Description                                                   |
|------------------------------------------|---------------------------------------------------------------|
| `search`                                 | Rules whose name contains the value.                          |
| `name`, `severity`, `alertOperationId`   | Rules where the attribute equals the value.                   |
| `sort`                                   | `name`, prefix with `-` for descending order.                 |

Send attributes as a flat JSON object. `POST` and `PUT` need every
required attribute, `PATCH` changes only the attributes it contains.

```curl
curl -X POST \
  -H 'Authorization: Bearer YOURAPITOKENHERE' \
  -H 'Content-Type: application/vnd.api+json' \
  -d '{"name": "Device Down", "severity": "critical", "builder": {"condition": "AND", "rules": [{"field": "devices.status", "operator": "equal", "value": "0"}]}}' \
  https://librenms.org/api/v1/alert-rules
```

## Adding custom endpoints

There are two places to add v1 functionality, depending on whether you
need a plain route or a full CRUD resource.

### 1. Custom (non-repository) endpoints

Routes that are not standard CRUD resources—health checks, actions,
reports, etc.—are declared by overriding `routes()` on a class in
`app/Restify/`. Restify discovers these classes and applies the configured
v1 prefix and middleware. Point the route at an invokable controller in
`app/Http/Controllers/Api/V1/`.

```php
// app/Restify/ExampleRepository.php
namespace App\Restify;

use App\Http\Controllers\Api\V1\ExampleController;
use Binaryk\LaravelRestify\Repositories\Repository as RestifyRepository;
use Illuminate\Routing\Router;

class ExampleRepository extends RestifyRepository
{
    public static string $uriKey = '';

    public static function routes(Router $router, array $attributes, $wrap = true): void
    {
        // Routes are authenticated by default.
        $router->get('example', ExampleController::class)
            ->name('api.v1.example');

        // Authentication must be explicitly removed for a public route.
        $router->get('public-example', ExampleController::class)
            ->withoutMiddleware(['auth:sanctum', 'can:api.access'])
            ->name('api.v1.public-example');
    }
}
```

A minimal controller:

```php
// app/Http/Controllers/Api/V1/ExampleController.php
namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use Illuminate\Http\JsonResponse;

class ExampleController extends Controller
{
    public function __invoke(): JsonResponse
    {
        return response()->json(['meta' => ['message' => 'example']]);
    }
}
```

Guidelines:

- Place controllers in `app/Http/Controllers/Api/V1/`.
- Routes inherit `auth:sanctum` and `can:api.access`. Remove them with
  `->withoutMiddleware(['auth:sanctum', 'can:api.access'])` only for
  intentionally public endpoints such as the health probe.
- Custom routes are not covered by model policies, so authorize inside the
  controller.
- Give custom routes a unique `api.v1.*` name.

### 2. Restify repository (CRUD) resources

For standard create/read/update/delete access to a model, add a Restify
repository in `app/Restify/`:

```php
// app/Restify/DeviceRepository.php
namespace App\Restify;

use App\Models\Device;

class DeviceRepository extends Repository
{
    public static string $model = Device::class;
}
```

Restify discovers the repository and generates the standard resource routes
(index, show, store, update, destroy) under `/api/v1` automatically. See the
[Laravel Restify documentation](https://restify.binarcode.com/) for how to
define repositories, fields, and authorization.

Model repositories extend `App\Restify\Repository`. The JSON:API `type` of
their resources is the endpoint name, and each request is authorized with
the model's policy in `app/Policies/`, the same policy the web UI uses:

| Request                  | Policy method |
|--------------------------|---------------|
| Any use of the resource  | `viewAny`     |
| Show a record            | `view`        |
| Create a record          | `create`      |
| Update a record          | `update`      |
| Delete a record          | `delete`      |

Bulk create, update and delete, and attach, detach and sync, are denied
unless the policy defines Restify's method for them. Write policies with
`lnms make:policy`, Restify's `restify:policy` generates methods this
mapping does not use.

Index results are only filtered per row after pagination, so a repository
whose records are not all visible to every user with `viewAny` must
restrict them in `indexQuery()` and `showQuery()`, usually with the model's
`hasAccess` scope. Restricting them in `mainQuery()` also limits which
records can be updated and deleted.

### After changing routes

Route and config are cached on container start, so after adding or changing
endpoints clear the caches:

```bash
php artisan route:clear
php artisan config:clear
```

Verify the result with `php artisan route:list --path=api/v1`.
