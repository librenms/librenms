# API v1 (Beta)

!!! warning "Beta"
    The v1 API is in **beta**. Endpoints and behaviour may change without
    notice while it is under active development. Full endpoint documentation
    is coming later — for now this page covers the basics and how to extend
    it. The stable, fully documented API remains [v0](index.md).

    The v1 API is disabled by default. Enable it with
    `lnms config:set api.v1.enabled true`, or in the web UI under
    **Settings → API → API v1 (Beta)**. When disabled, all `/api/v1`
    endpoints return 404.

## Overview

The v1 API is served under the `/api/v1` prefix and is built on
[Laravel Restify](https://restify.binarcode.com/) with
[Sanctum](https://laravel.com/docs/sanctum) bearer-token authentication.

## Authentication

Most v1 endpoints require a personal access token sent as a standard Bearer token:

```curl
curl -H 'Authorization: Bearer YOURAPITOKENHERE' https://librenms.org/api/v1/system
```

Create an API token from the web interface at `/api-access/` (**Settings → API Settings → API Access**). Note that `X-Auth-Token` is only supported on API v0 endpoints; API v1 strictly requires the `Authorization: Bearer` header.

## Available endpoints

| Method         | Path                       | Auth                       | Description                                      |
|----------------|----------------------------|----------------------------|--------------------------------------------------|
| `GET`          | `/api/v1/health`           | none (public)              | Rate-limited readiness probe.                    |
| `GET`          | `/api/v1/system`           | bearer token               | Application version and database row statistics. |
| `GET`          | `/api/v1/alert-rules`      | bearer token, `api.access` | List alert rules.                                |
| `POST`         | `/api/v1/alert-rules`      | bearer token, `api.access` | Create an alert rule.                            |
| `GET`          | `/api/v1/alert-rules/{id}` | bearer token, `api.access` | Show a single alert rule.                        |
| `PUT`, `PATCH` | `/api/v1/alert-rules/{id}` | bearer token, `api.access` | Update an alert rule.                            |
| `DELETE`       | `/api/v1/alert-rules/{id}` | bearer token, `api.access` | Delete an alert rule.                            |

More endpoints will be added as the v1 API matures.

## Permissions

Resource endpoints (currently alert rules) require the `api.access`
permission in addition to a valid token; without it every request to the
resource returns 403. What a user may do within a resource is then decided
by that model's policy, using the same permissions as the web UI.

## Errors

Every v1 error is returned as a [JSON:API](https://jsonapi.org/format/#errors)
document with the `application/vnd.api+json` content type and an `errors`
array:

```json
{
  "errors": [
    {
      "status": "404",
      "code": "not_found",
      "title": "Not Found",
      "detail": "No query results for model [App\\Models\\AlertRule]."
    }
  ]
}
```

`status` is the HTTP status as a string, `code` is a stable machine-readable
identifier, and `detail` is a human-readable message.

| Status | `code`                | Cause                                                         |
|--------|-----------------------|---------------------------------------------------------------|
| 401    | `unauthenticated`     | Missing or invalid bearer token.                              |
| 403    | `forbidden`           | The user lacks `api.access` or the required model permission. |
| 404    | `not_found`           | Unknown resource or record, or the v1 API is disabled.        |
| 405    | `method_not_allowed`  | The HTTP method is not supported on this path.                |
| 422    | `validation_failed`   | The request body failed validation.                           |
| 429    | `too_many_requests`   | Rate limit exceeded.                                          |
| 503    | `service_unavailable` | A required service, such as the database, is unavailable.     |
| 500    | `server_error`        | Unexpected error.                                             |

Other HTTP errors use the code `http_<status>`.

Validation failures return one entry per failed rule, each with a
`source.pointer` naming the offending attribute:

```json
{
  "errors": [
    {
      "status": "422",
      "code": "validation_failed",
      "title": "Validation Failed",
      "detail": "The name field is required.",
      "source": { "pointer": "/name" }
    },
    {
      "status": "422",
      "code": "validation_failed",
      "title": "Validation Failed",
      "detail": "The selected severity is invalid.",
      "source": { "pointer": "/severity" }
    }
  ]
}
```

For server errors the `detail` is a generic message. When `APP_DEBUG` is
enabled, the real exception message is returned and a `meta` object with
the exception class, file, line and a short trace is added to the entry.

### Health

`GET /api/v1/health` is public so it can report a failure even when
database-backed token authentication is unavailable. Its response is
deliberately generic: it does not identify dependencies or include exception
messages, application details, or user information. Requests are limited to
60 per minute per client.

A healthy response returns HTTP 200:

```json
{
  "meta": {
    "status": "healthy"
  }
}
```

An unavailable dependency returns a generic HTTP 503:

```json
{
  "errors": [
    {
      "status": "503",
      "title": "Service Unavailable",
      "detail": "A required service is unavailable."
    }
  ]
}
```

### System

`GET /api/v1/system` requires a bearer token. It returns application
identity and selected table row counts:

```json
{
  "meta": {
    "application": {
      "name": "LibreNMS",
      "version": "26.7.0"
    },
    "statistics": {
      "devices": 42,
      "ports": 512,
      "users": 3
    }
  }
}
```

If the database is unavailable during authentication or while gathering
statistics, the endpoint returns the same generic JSON:API 503 error used by
the health endpoint. Database connection details are never included.

### Alert rules

`/api/v1/alert-rules` provides create, read, update and delete access to
alert rules. All requests require a bearer token for a user with the
`api.access` permission, plus the alert rule permission for the operation:

| Operation  | Permission                                                                                  |
|------------|---------------------------------------------------------------------------------------------|
| List, show | `alert-rule.viewAll`, or `alert-rule.view` for rules mapped to devices the user can access. |
| Create     | `alert-rule.create`                                                                         |
| Update     | `alert-rule.update`                                                                         |
| Delete     | `alert-rule.delete`                                                                         |

A rule is returned as a resource object with its attributes:

```json
{
  "data": {
    "id": "12",
    "type": "alert_rules",
    "attributes": {
      "name": "Device Unreachable",
      "severity": "critical",
      "isEnabled": true,
      "query": "devices.status = 0",
      "builder": {
        "condition": "AND",
        "rules": [
          { "id": "devices.status", "operator": "equal", "value": 0 }
        ]
      },
      "isConditionInverted": false,
      "isMuted": false,
      "sendsRecoveryAlerts": true,
      "sendsAcknowledgementAlerts": true,
      "overridesQuery": false,
      "procedure": null,
      "notes": null,
      "isScopeInverted": false,
      "alertOperationId": null
    }
  }
}
```

| Attribute                    | Type            | Description                                                              |
|------------------------------|-----------------|--------------------------------------------------------------------------|
| `name`                       | string          | Required. At most 255 characters.                                        |
| `severity`                   | string          | Required. One of `ok`, `warning`, `critical`.                            |
| `isEnabled`                  | boolean         | Required. Whether the rule is evaluated.                                 |
| `query`                      | string or null  | The SQL query of the rule.                                               |
| `builder`                    | object or null  | The rule builder definition.                                             |
| `isConditionInverted`        | boolean         | Invert the rule match. Defaults to `false`.                              |
| `isMuted`                    | boolean         | Mute alerts for this rule. Defaults to `false`.                          |
| `sendsRecoveryAlerts`        | boolean         | Send an alert when the rule recovers. Defaults to `true`.                |
| `sendsAcknowledgementAlerts` | boolean         | Send an alert when the rule is acknowledged. Defaults to `true`.         |
| `overridesQuery`             | boolean         | Use `query` as written instead of the builder. Defaults to `false`.      |
| `procedure`                  | string or null  | Procedure text or URL. At most 80 characters.                            |
| `notes`                      | string or null  | Free-form notes.                                                         |
| `isScopeInverted`            | boolean         | Invert the device, group and location mapping. Defaults to `false`.      |
| `alertOperationId`           | integer or null | ID of an existing alert operation.                                       |

#### Listing

`GET /api/v1/alert-rules` returns a paginated `data` array of rules along
with `meta` (including `total`, `current_page`, `per_page` and
`last_page`) and `links`. It accepts these query parameters:

| Parameter                              | Description                                                   |
|----------------------------------------|---------------------------------------------------------------|
| `search`                               | Match rules whose name contains the value.                    |
| `name`, `severity`, `query`, `notes`   | Match rules where the attribute equals the value.             |
| `sort`                                 | Sort by `name` or `severity`; prefix with `-` for descending. |
| `perPage`, `page`                      | Page size and page number.                                    |

```curl
curl -H 'Authorization: Bearer YOURAPITOKENHERE' \
  'https://librenms.org/api/v1/alert-rules?severity=critical&sort=-name&perPage=25'
```

#### Creating and updating

Send the attributes as a flat JSON object, with a `Content-Type` of
`application/vnd.api+json` or `application/json`. A successful create
returns HTTP 201 with the new rule, an update returns HTTP 200 with the
updated rule, and a delete returns HTTP 204 with no body.

```curl
curl -X POST \
  -H 'Authorization: Bearer YOURAPITOKENHERE' \
  -H 'Content-Type: application/vnd.api+json' \
  -d '{"name": "Device Unreachable", "severity": "critical", "isEnabled": true, "query": "devices.status = 0"}' \
  https://librenms.org/api/v1/alert-rules
```

## Adding custom endpoints

There are two places to add v1 functionality, depending on whether you
need a plain route or a full CRUD resource.

### 1. Custom (non-repository) endpoints

Routes that are not standard CRUD resources—health checks, actions,
reports, etc.—are declared by overriding `routes()` on a class in
`app/Restify/`. Restify discovers these classes and applies the configured
v1 prefix and middleware. Point the route at an invokable controller in
`app/Http/Controllers/Api/V1/`.

```php
// app/Restify/ExampleRepository.php
namespace App\Restify;

use App\Http\Controllers\Api\V1\ExampleController;
use Illuminate\Routing\Router;

class ExampleRepository extends Repository
{
    public static string $uriKey = '';

    public static function routes(Router $router, array $attributes, $wrap = true): void
    {
        // Routes are authenticated by default.
        $router->get('example', ExampleController::class)
            ->name('api.v1.example');

        // Authentication must be explicitly removed for a public route.
        $router->get('public-example', ExampleController::class)
            ->withoutMiddleware('auth:sanctum')
            ->name('api.v1.public-example');
    }
}
```

A minimal controller:

```php
// app/Http/Controllers/Api/V1/ExampleController.php
namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use Illuminate\Http\JsonResponse;

class ExampleController extends Controller
{
    public function __invoke(): JsonResponse
    {
        return response()->json(['meta' => ['message' => 'example']]);
    }
}
```

Guidelines:

- Place controllers in `app/Http/Controllers/Api/V1/`.
- Routes inherit `auth:sanctum`. Remove it with
  `->withoutMiddleware('auth:sanctum')` only for intentionally public
  endpoints such as the health probe.
- Give custom routes a unique `api.v1.*` name.

### 2. Restify repository (CRUD) resources

For standard create/read/update/delete access to a model, add a Restify
repository in `app/Restify/`:

```php
// app/Restify/DeviceRepository.php
namespace App\Restify;

use App\Models\Device;

class DeviceRepository extends Repository
{
    public static string $model = Device::class;
}
```

Restify discovers the repository and generates the standard resource routes
(index, show, store, update, destroy) under `/api/v1` automatically. See the
[Laravel Restify documentation](https://restify.binarcode.com/) for how to
define repositories, fields, and authorization.

Repositories extend the base class `App\Restify\Repository`, which applies
the access rules shared by all v1 resources:

- The user must hold the `api.access` permission to use the repository at
  all.
- Index requests are authorized against the model policy's `viewAny`
  method, which Restify does not check by itself.

Every other operation is authorized by the model's policy in
`app/Policies/`, so a model needs a policy before its repository is usable.
`app/Restify/AlertRuleRepository.php` is a complete example with fields,
validation rules, search, match filters and sorting.

### After changing routes

Route and config are cached on container start, so after adding or changing
endpoints clear the caches:

```bash
php artisan route:clear
php artisan config:clear
```

Verify the result with `php artisan route:list --path=api/v1`.
